# Spec — i18n architecture: PT-BR and EN with a language switch

> Resolves wayfinder ticket **i18n architecture — PT-BR and EN with a switch**
> (`.wayfinder/tickets/016-i18n-architecture.md`). Map: `.wayfinder/map.md`.
> Status: **ready-for-agent**. This is a spec, not an implementation — no app
> code, dependencies, or config were changed to produce it.

## The hard part: SEO under static export with two locales

WattSteer static-exports (`apps/web/app.json` → `"web": { "output": "static" }`)
and ships the same source to iOS/Android. That rules out a server that could
inspect `Accept-Language` per request — the web output is a directory of
prebuilt HTML files served by a dumb static server (`apps/web/server.ts`),
and Dockerfile confirms it: build produces `dist/`, runtime just serves it.
Whatever locale strategy is chosen has to resolve entirely at **export time**
or entirely on the **client**, never on a request-time server decision.

That is exactly the fork the ticket names: locale-prefixed routes (crawlable,
duplicated static output) vs. client-side switching (one bundle, invisible
second language). **Decision: locale-prefixed routes, both locales prefixed
symmetrically — `/pt/...` and `/en/...` — with a thin, static, non-indexed
gate page at bare `/`.**

### What expo-router (`~57.0.3`, installed per `apps/web/package.json`) actually supports

Verified against current Expo docs (`docs.expo.dev/router/web/static-rendering/`,
fetched during this ticket):

- **`generateStaticParams` is real and is the mechanism.** A dynamic segment
  file (e.g. `app/[locale]/index.tsx`) exports `generateStaticParams`
  returning an array of param objects; the static exporter calls it at build
  time in Node and emits one HTML file per returned param set. The docs' own
  example: `[{ id: "alpha" }, { id: "beta" }]` on `app/[id].tsx` produces
  `dist/blog/alpha.html` and `dist/blog/beta.html`. For WattSteer,
  `app/[locale]/index.tsx` returning `[{ locale: "pt" }, { locale: "en" }]`
  is the same shape and should produce `dist/pt.html`-equivalent output per
  locale (confirm the exact nesting — see Open Questions; a folder segment
  most likely exports as `dist/pt/index.html`, matching how the existing
  `index.tsx` exports as `dist/index.html`).
- **Params cascade to nested dynamic children.** A `[locale]` segment's value
  is available to every route nested under it, so `app/[locale]/privacy.tsx`
  and `app/[locale]/terms.tsx` each get `generateStaticParams` returning the
  same two locales (or a shared helper) and multiply out correctly — 2
  locales × 3 pages = 6 static HTML files, plus the gate page.
- **No serverless fallback exists.** Only params returned by
  `generateStaticParams` get a page; anything else 404s. This is fine here —
  the locale set is fixed (`pt`, `en`), not user-generated.
- **`<Head>` (from `expo-router/head`) is per-route and confirmed to support
  per-page metadata** — the existing `index.tsx`/`legal-screen.tsx` already
  prove this (canonical link, OG tags, `robots` meta all vary today). Each
  locale's rendered page can carry its own `<title>`, `<meta name="description">`,
  canonical URL, and `hreflang` alternates.
- **`+html.tsx` is a single global document shell, confirmed NOT per-route.**
  This is the one real wrinkle. Expo's own docs describe it as wrapping
  "all routes in the app directory" with no per-route parameterization, and
  the current file hardcodes `<html lang="en">`. That means the `lang`
  attribute — which matters for accessibility and for search engines'
  language signal — **cannot be set correctly per locale from React alone**
  during static export. See Open Questions for the workaround.

This confirms the ticket's framing was correct to treat this as a real
routing decision, not a copy decision: the two builds are structurally
different, and expo-router's static exporter is the tool that makes the
prefixed-route option tractable without hand-rolling a second export pass.

### Route layout (target shape)

```
apps/web/src/app/
  index.tsx              # gate page — see below. Bare "/". NOT under [locale].
  [locale]/
    _layout.tsx           # validates locale ∈ {pt, en}; provides i18n context
    index.tsx             # today's landing page content, locale-aware
    privacy.tsx
    terms.tsx
  _layout.tsx             # root layout (ThemeProvider, StatusBar) — unchanged shape
  +html.tsx               # unchanged mechanism, see lang-attribute note
  +not-found.tsx          # global fallback (see Open Questions on scoping it)
```

`app/[locale]/_layout.tsx` is where `generateStaticParams` for the segment
lives (or a shared constant re-exported by each leaf — cascading means
declaring it once at the segment layout should suffice; confirm during
implementation), and where the route's `locale` param is validated and
threaded into the i18n provider — never re-derived from the browser inside
this subtree. **The URL is the single source of truth for what locale a given
static page is; browser/device locale only decides where the gate page sends
a first-time visitor.**

### The gate page (`/`)

A visitor to bare `wattsteer.com/` needs something crawlable and fast, not a
blank redirect. The gate page is a minimal static route (`app/index.tsx`,
outside the `[locale]` tree) that ships:

1. Visible, real `<a>`-equivalent `Link`s to `/pt/` and `/en/` — so it is
   fully functional with JavaScript disabled and gives any crawler an
   immediate, real path to both locales. This is the concrete difference from
   plain client-side switching: even the "gate" degrades to a crawlable page,
   never a blank shell.
2. A small client-side script that reads a persisted preference
   (`localStorage`) or, failing that, `navigator.language` / `expo-localization`,
   and replaces the URL to `/pt/` or `/en/` for a real visitor — so humans
   never actually see the gate twice.
3. `<meta name="robots" content="noindex,follow">` — the gate itself is not a
   destination worth ranking (it has no unique content), but `follow` lets
   crawl equity flow to the two real locale roots it links to.
4. `hreflang` alternates: `pt-BR` → `/pt/`, `en` → `/en/`, `x-default` → `/pt/`
   (Brazil is the primary market per the map's audience framing; PT-BR is the
   default when a crawler or user-agent expresses no preference).

`robots.txt` stays `Allow: /` — do **not** add a `Disallow` for the gate.
Combining `Disallow` with a `noindex` meta tag is a known anti-pattern: a
disallowed page can't be crawled, so Google never sees the `noindex` directive
and may still index the URL from external links with no snippet. `noindex`
alone is the correct and suf1ficient signal here.

### `sitemap.xml`

Regenerate to list only the real, indexable pages — six URLs, not the gate:

```
/pt/, /pt/privacy, /pt/terms, /en/, /en/privacy, /en/terms
```

At this scale (six URLs, stable set) hand-maintaining the file as today is
fine; there is no dynamic content driving page count. If/when this grows,
revisit generating it as a build step. Each `<url>` should carry
`<xhtml:link rel="alternate" hreflang="...">` entries pointing at its sibling
locale (the standard hreflang-in-sitemap pattern, requiring the
`xmlns:xhtml="http://www.w3.org/1999/xhtml"` namespace on `<urlset>`), which
duplicates the per-page `<link rel="alternate" hreflang>` tags already
recommended in each page's `<Head>` — sitemap and in-page hreflang should
agree, since disagreement between them is a common source of hreflang being
silently ignored by Google.

### `manifest.webmanifest`

A single manifest can't carry two names/descriptions. Ship two files —
`manifest.pt.webmanifest` and `manifest.en.webmanifest` — each with its own
`name`, `short_name`, `description`, and a `lang` field, and stop declaring
`<link rel="manifest">` in `+html.tsx` (which is global and can't vary).
Instead, each `[locale]/_layout.tsx` (or every leaf route's `<Head>`) emits
exactly one `<link rel="manifest" href="/manifest.pt.webmanifest">` (or `.en.`)
— see Open Questions on why this must be the *only* manifest link on the page
rather than an override of a global one.

### `EXPO_PUBLIC_*` / Dockerfile — mostly unaffected

Good news: locale switching here is either build-time-static (which
`generateStaticParams` route already resolves per file) or client-side
runtime (i18next resource selection, `localStorage`), so no new
`EXPO_PUBLIC_*` variable or Dockerfile build arg is needed. `EXPO_PUBLIC_SITE_URL`
(already inlined at build time per the Dockerfile's `ARG`/`ENV` pair) now
gets used to build twice as many canonical/hreflang URLs (locale-prefixed),
which is a code change inside `apps/web/src/lib/config.ts`-equivalent, not an
infra change. The one real chore: `apps/web/public/llms.txt`,
`robots.txt`, and `sitemap.xml` are static files copied verbatim by the
Dockerfile (`COPY apps/web/public ./apps/web/public`) — they must be hand-
updated when the locale routes ship (`llms.txt` in particular should list
both `/pt/` and `/en/` as entry points, not just the historical `/`).

### Playwright legal suite (`apps/web/e2e/legal.spec.ts`, `playwright.config.ts`)

Every test in the current suite assumes unprefixed routes: it `goto`s `/`,
`/terms`, `/privacy`, and asserts the home link returns to `/`. All of that
breaks. Required rework (implementation, not part of this spec):

- Wrap the existing `for (const path of ["/terms", "/privacy"])` loop in an
  outer `for (const locale of ["pt", "en"])`, testing `/${locale}${path}`.
- `footer-privacy-link` / `footer-terms-link` / `legal-home-link` need to
  resolve relative to the *current* locale (a `Link href="/privacy"` hardcoded
  today must become locale-aware, e.g. `` href={`/${locale}/privacy`} ``) —
  a real code change the tests should catch if missed.
- A new small suite for the gate page: assert it redirects to `/pt/` (default,
  no stored/detected preference) and to `/en/` when `navigator.language`/
  storage indicates English, and that both static links are present and
  clickable even before the redirect script runs.

## i18n library

**`i18next` + `react-i18next`**, with the built-in browser language-detector
plugin **disabled**. Reasoning:

- Works identically on web (react-native-web) and native (iOS/Android) — the
  same `useTranslation()` hook and resource-bundle shape run everywhere,
  which matters because WattSteer ships the same source to app stores.
- It has no server dependency and no build-time code generation step, so it
  survives static export unmodified — resource JSON is just data bundled
  into the client JS like any other asset.
- Locale here must be **derived from the route** (`[locale]` param), not
  autodetected in the browser after hydration — autodetection racing against
  server-rendered HTML is exactly what causes hydration mismatches and
  (worse for SEO) a flash where a crawler's snapshot and the post-hydration
  DOM disagree on language. So i18next's own detector plugin is not used;
  each `[locale]/_layout.tsx` calls `i18n.changeLanguage(locale)` from the
  validated route param, synchronously, before rendering children.
- The **gate page** (`/`, outside the locale tree) is the only place actual
  device/browser detection happens (`expo-localization`'s `getLocales()` on
  native, `navigator.language` on web), purely to pick a redirect target, and
  only when there is no persisted choice yet.

**Persistence**: the chosen/visited locale is written to `localStorage` (web)
/ a small `AsyncStorage` key (native, via `expo-localization`'s
recommendation or plain `@react-native-async-storage/async-storage`) whenever
a user actively switches languages via the in-app switch, so a returning
visitor's explicit choice overrides the default. This is the only piece of
i18n state that lives in storage — everything else is derived from the URL.

**Does the switch change the URL?** Yes — the language switch is a `Link` to
the same page under the other locale prefix (`/en/privacy` ⇄ `/pt/privacy`),
not a state toggle. This is required for the whole SEO argument to hold: if
switching didn't change the URL, the two languages would collapse back into
"one URL, client-side state," which is precisely the failure mode being
designed around.

## Where strings live, and stopping hardcoded English

Resource files as `apps/web/src/i18n/{en,pt}/*.json` (or a shared
`packages/core` location if the API's LLM narration prompts want to reuse the
same terminology dictionary later — worth revisiting once that surface is
built), organized by namespace (`common`, `legal`, `landing`, per-screen as
the four `/app` product screens land). `useTranslation("namespace")` +
`t("key")` everywhere; no inline English/Portuguese string literals in JSX.

**Enforcement**: the repo already has a working pattern for exactly this
class of problem — `test/repo-hygiene.test.ts` currently fails the build if
the string `"zalytix"` reappears anywhere in project code, walking the tree
with an explicit exemption list. Extend that same test (or add a sibling
`test/i18n-hardcoded-copy.test.ts`) with a heuristic scan of `apps/web/src/**/*.tsx`
for JSX text nodes / string literal props (`label=`, `title=`, `placeholder=`)
that contain alphabetic runs and are **not** wrapped in a `t(...)` call,
excluding files under `src/i18n/` and a short allow-list for the untranslated
domain terms below. This won't be airtight (a regex-based JSX scan can't
perfectly parse React), but it matches the existing hygiene-test philosophy
in this repo — catch the common case cheaply, accept it's a heuristic, don't
block on building a real AST linter for two locales. The repo uses Biome, not
ESLint, so `eslint-plugin-i18next`'s `no-literal-string` rule (the standard
tool for this) is not directly available; a bespoke Bun test is the pragmatic
substitute given the existing toolchain.

## Number, date, and unit formatting

Use native `Intl`, not a formatting library, keyed off two full locale tags:

- **`pt-BR`** for the Portuguese locale (not bare `pt` — decimal-comma,
  thousands-period, and `R$` symbol placement are specifically pt-BR
  conventions, not shared by pt-PT).
- **`en-US`** for English (an arbitrary but reasonable pick; the ticket does
  not specify a English sub-locale and the audience is global
  English-reading engineers, not a specific English-speaking country).

Concretely:

- **Decimals/grouping** — `new Intl.NumberFormat(locale).format(n)` handles
  the comma/period swap automatically (`1234.5` → `"1.234,5"` in `pt-BR`,
  `"1,234.5"` in `en-US`). No manual string manipulation.
- **MW / MWh** — do **not** use `Intl.NumberFormat`'s `style: "unit"` for
  these. ECMA-402's sanctioned unit list is a fixed CLDR set and does not
  include "megawatt" or "megawatt-hour" as simple units usable directly with
  natural pluralized labels the way "kilometer" or "celsius" are — verify
  before relying on it (see Open Questions). Safer, and what the map's own
  KPI framing already implies (MWh recovered, % avoided as headline figures):
  format the number with plain `Intl.NumberFormat(locale)` and append the
  unit as a literal, locale-invariant suffix string (`"MWh"`, `"MW"`) — these
  are not translated in either locale (see domain terms, below).
- **R$ / currency** — `Intl.NumberFormat(locale, { style: "currency", currency: "BRL" })`.
  Currency is always `BRL` regardless of UI locale (the map is explicit: R$
  appears only as a labelled economic scenario with the assumed R$/MWh
  visible — this is Brazilian-grid economics shown to an English reader, not
  a currency conversion). Locale only changes the grouping/decimal
  convention and symbol placement, never the currency itself.
- **Dates/times** — `Intl.DateTimeFormat(locale, { timeZone: "America/Sao_Paulo", ... })`.
  The timezone is **fixed to Brasília time regardless of UI locale** — an
  English-reading operator is still looking at the Brazilian grid, and
  `din_instante` (per the ONS dataset inventory finding) is already
  documented as Brasília local civil time. Only month/weekday names and
  date-part ordering should follow the UI locale; the timezone must not.

## Domain terms that stay untranslated in both locales

Per the map's standing decision: **"curtailment"** has no clean Portuguese
equivalent, and ONS's own vocabulary for the phenomenon is **"constrained-off"**
— itself an English term, used natively in the sector's own Portuguese-language
discourse. This is the one term explicitly settled by the dev and it is the
load-bearing example: **"curtailment" / "constrained-off" render identically
in the `pt` and `en` resource bundles** — they are not translation keys with
two values, they are literal strings shared by both locales (or, more
precisely, present in the `pt` bundle already in English, not translated
into anything else).

By the same logic (ONS/ANEEL/ANEEL-SIGA/DESSEM's own vocabulary, proper nouns
and acronyms that don't have — and shouldn't get — an English or Portuguese
counterpart), the following should be treated the same way and are worth an
explicit allow-list entry rather than being silently caught by the hygiene
scan above: **ONS, ANEEL, SIN, SIGA, DESSEM, BESS, SOC** (state of charge),
and **conjunto** (the reporting-entity grain the map's decisions establish as
its own domain concept, distinct from a plant — translating it to "grouping"
or "cluster" in English would blur a distinction the domain model depends on,
so "conjunto" should probably appear as-is in English copy too, glossed on
first use rather than translated). This list should be treated as a
starting point, not exhaustive — it will grow as the four `/app` screens are
built and more ONS-native vocabulary shows up in real copy.

## Does the API return translated strings, or only codes?

**Codes only, with one deliberate exception.** For structured data — reason
codes (`REL`/`CNF`/`ENE`/`PAR`), subsystem identifiers, asset types, any
enum-shaped value — the API returns the code, and the client renders it
through the same locale-aware string tables as everything else. This keeps
the API a single source of truth regardless of which locale a client
requests in, and matches the general principle that domain codes are not
UI copy.

**The exception**: the map's stack decision already commits `apps/api` to
"the LLM narration call" (the Explain screen's grid-conditions narration).
That narration is **generated prose, not a fixed string catalog** — there is
no `t()` key for a sentence an LLM writes fresh per request. For that surface
specifically, the API should accept a `locale` parameter and generate the
narration directly in the requested language (a prompt-level instruction),
returning natural-language text the client renders as-is. This is a genuine
exception to "codes only," worth calling out explicitly so a future session
doesn't either (a) try to force LLM narration through the client-side
translation-key system, which can't work for generated prose, or (b) quietly
assume the whole API is locale-blind because the rest of it is.

## Open questions / could not confirm

- **Exact static-export file layout for `[locale]/index.tsx`.** The Expo docs
  confirm the mechanism (`generateStaticParams` → one file per param set) but
  the worked example in the docs is a flat `[id].tsx`, not a folder segment
  containing an `index.tsx`. Whether the output is `dist/pt/index.html`,
  `dist/pt.html`, or something else needs a real `expo export --platform web`
  run to confirm before implementation relies on a specific path for the
  static server (`server.ts`)'s fallback logic.
- **`<html lang>` per locale during static export.** Confirmed `+html.tsx` is
  a single global shell with no documented per-route parameterization. The
  practical workaround — a small post-`expo export` script that rewrites
  `lang="en"` to the correct value in each `dist/{locale}/**/*.html` file
  before the Docker image is built — was not tested here and is not
  documented anywhere as a sanctioned Expo pattern; it's an inference from
  the fact that the export output is plain static HTML. Confirm there isn't
  a cleaner supported mechanism before building this (e.g. a newer expo-router
  minor version, since `~57.0.3` allows patch/minor bumps within `57.x`).
- **Whether `expo-router/head`'s per-route tag injection dedupes or appends**
  when a tag with the same `rel` (e.g. `manifest`, or `alternate`/`hreflang`)
  is emitted from more than one place in the tree. This spec avoids the
  question by only ever emitting each such tag from exactly one place per
  page, but that constraint should be verified, not assumed, the first time
  it's implemented.
- **Whether `+not-found.tsx` can be scoped per directory** (i.e. a
  `[locale]/+not-found.tsx` giving a localized 404 for unknown paths under a
  given locale prefix, vs. one global English-only 404 for everything). Not
  confirmed against current expo-router docs. If it isn't supported, the
  fallback — one global, English-only 404 already `noindex`ed — is an
  acceptable v1 compromise, not a blocker.
- **Whether ECMA-402's sanctioned unit list actually excludes "megawatt"/
  "megawatt-hour"** as asserted above. This was reasoned from general
  knowledge of the CLDR unit list's typical contents (kilometer, celsius,
  etc.) rather than verified against the current spec text; the recommendation
  to hand-append `"MW"`/`"MWh"` as literal suffixes is safe either way (it
  works regardless of whether `style: "unit"` would also have worked), so
  this doesn't block anything, but it's worth a two-minute check before
  anyone spends time trying to make `Intl` do the unit formatting natively.
- **PWA manifest `lang` field interaction with browser install prompts** when
  two manifests exist for one origin. Not verified — this is a minor,
  non-blocking cosmetic risk (worst case, an installed PWA shows the wrong
  language in its OS-level app name until the manifest is re-fetched).
